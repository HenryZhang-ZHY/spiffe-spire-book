# 第 9 章　SPIFFE 与其他安全技术的比较

本章将 SPIFFE 与解决类似问题的其他技术进行比较。

## 引言

SPIFFE 和 SPIRE 所解决的问题并非新问题。每个分布式系统为了保障安全，都必须具备某种形式的身份机制。Web 公钥基础设施（Web PKI）、Kerberos/Active Directory、OAuth、密钥存储以及服务网格都是典型例子。

然而，这些现有的身份形式并不适合用于标识组织内部的服务。对于典型的内部部署而言，Web PKI 不仅实施困难，而且不够安全。作为 Active Directory 认证组件的 Kerberos 需要始终在线的票据授予服务器（Ticket Granting Server），并且没有任何等效的验证机制。服务网格、密钥管理器和覆盖网络都只解决了服务身份难题的一部分，并不完整。目前，SPIFFE 和 SPIRE 是服务身份问题的唯一完整解决方案。

## Web 公钥基础设施（Web PKI）

Web 公钥基础设施（Web Public Key Infrastructure，Web PKI）是一种被广泛使用的方法，用于让 Web 浏览器安全连接到目标网站。它利用 X.509 证书来断言用户连接到的正是其打算访问的网站。由于你很可能已经熟悉这一模型，自然会提出一个合理的问题：为什么我们不能使用 Web PKI 来为组织内部的服务提供身份标识？

在传统的 Web PKI 中，证书的签发和续期完全是手动流程。这些手动流程非常不适合现代基础设施，因为在现代基础设施中，服务实例随时可能动态扩缩。不过，近几年来，Web PKI 已转向一种名为域名验证（Domain Validation，DV）的自动化证书签发与续期流程。

在 DV 流程中，证书颁发机构（CA）会向证书请求方发送一个令牌。证书请求方通过 HTTP 服务器对外提供该令牌。CA 访问并校验该令牌后，再签发证书。

这种机制的第一个问题在于，内部服务通常没有独立的 DNS 名称或 IP 地址。如果希望在所有服务之间实施 mTLS（双向 TLS），那么就连客户端也需要拥有 DNS 名称才能获取证书，这在配置上极具挑战性。在同一台主机上运行的多个服务若要各自获得身份标识，就需要分配不同的 DNS 名称，这同样难以配置。

一个更隐蔽的问题是，任何能够成功响应令牌请求的对象，都可以成功获取证书。这个对象可能是运行在同一台服务器上的其他服务，甚至是位于另一台服务器上、能够篡改本地二层网络的服务。

总的来说，尽管 Web PKI 在互联网安全网站场景下表现出色，但它并不适合用于服务身份标识。许多需要证书的内部服务并没有 DNS 名称。一旦攻击者成功渗透本地网络中的任何服务，当前可用的证书校验流程就很容易被攻破。

## Active Directory（AD）与 Kerberos

Kerberos 是一种最初于 20 世纪 80 年代末由麻省理工学院（MIT）开发的认证协议。它最初旨在通过集中式用户数据库实现人到服务的认证。后来，Kerberos 进行了扩展，除用户账户外，还支持服务到服务的认证以及机器账户的使用。Kerberos 协议本身并不依赖于特定的账户数据库。不过，Kerberos 最常见的应用场景是在 Windows 域中，使用 Active Directory（AD）作为账户数据库进行认证。

Kerberos 的核心凭据称为票据（ticket）。票据是一种供单个客户端访问单个资源使用的凭据。客户端通过调用票据授予服务（Ticket Granting Service，TGS）来获取票据。客户端每访问一个资源，都需要获取一张新票据。这种设计会导致协议交互过于频繁，并降低可靠性。

所有服务都与 TGS 存在信任关系。当服务向 TGS 注册时，会与 TGS 共享密钥材料（例如对称密钥或公钥）。TGS 使用该密钥材料来创建用于认证该服务访问权限的票据。轮换密钥材料需要服务与 TGS 之间相互协调：服务必须继续接受并记住先前的密钥材料，以确保现有票据仍然有效。

### SPIRE 如何缓解 Kerberos 与 AD 的缺陷

在 SPIRE 中，每个客户端和资源只需调用一次 SPIRE Server 即可获取自身凭据（SVID，SPIFFE 可验证身份文档），随后信任域（及联邦信任域）内的所有资源都可以验证这些凭据，而无需再次调用 SPIRE Server。SPIRE 的架构避免了每访问一个资源都要获取新凭据所带来的开销。

像 SPIRE 这样基于 PKI（公钥基础设施）的认证机制使凭据轮换变得更加简单，因为服务与集中式认证器之间不存在上述密钥材料协调问题。

最后值得一提的是，Kerberos 协议将服务与主机名紧密耦合，这使得单主机多服务以及集群部署变得复杂。相反，SPIRE 可以轻松支持单个工作负载拥有多个 SVID 以及集群场景，同时也支持将同一个 SVID 分配给多个工作负载。这些特性提供了一种健壮且高度可扩展的身份管理方式。

## OAuth 与 OpenID Connect（OIDC）

OAuth 是一种旨在实现访问委托的协议，其本身并不必然用于直接提供认证功能。OIDC 的主要目的是允许人类用户授权某个次级网站（或移动应用）代表自己访问另一个主网站。在实践中，由于被委托的访问凭据（在 OAuth 协议中即访问令牌）是由主网站出具的、证明用户已在该主网站完成认证的凭证，因此该协议得以在次级网站上实现用户认证。

如果主网站在访问令牌中包含了用户信息，或提供了通过访问令牌获取用户信息的方式，次级网站就可以使用主网站的令牌来认证用户。OpenID Connect 作为一种带有明确规范约定的 OAuth 变体，就是一个很好的例子。

OAuth 是面向人类用户而非非人实体（non-person entities）设计的。OAuth 登录流程需要通过浏览器重定向并交互式输入密码。OAuth 2.0 与其前身类似，但增加了对非人实体的支持，通常通过创建服务账户（即代表工作负载而非人类的用户身份）来实现。

当工作负载希望获取 OAuth 访问令牌以访问远程系统时，必须使用 OAuth 客户端密钥、密码或刷新令牌向 OAuth 提供方进行认证，从而获取访问令牌。所有工作负载都应拥有独立的凭据，以实现高粒度的工作负载身份管理。但在弹性计算环境中，由于每个工作负载和身份都必须向 OAuth 提供方注册，这类凭据的管理很快就会变得复杂而困难。长期有效的密钥在需要吊销时会引入更多复杂性。因轮换而在环境中分发密钥会降低基础设施的灵活性；在某些情况下，如果由开发人员手动管理密钥，还可能带来攻击面。

### SPIFFE 与 SPIRE 如何缓解 OAuth 与 OIDC 的复杂性

依赖预先存在的凭据（如 OAuth 客户端密钥或刷新令牌）来标识工作负载，无法解决底层乌龟问题（如第 1 章所述）。在这些场景下，利用 SPIRE 作为身份提供方，可以在联系 OAuth 基础设施之前先行签发引导凭据（即“底层乌龟”）。

由于无需将长期有效的静态凭据与工作负载本身一同部署，SPIRE 显著提升了安全性。SPIFFE 可以与 OAuth 形成互补：它消除了直接管理 OAuth 客户端凭据的需求——应用可以在需要时使用其 SPIFFE ID 向 OAuth 提供方进行认证。事实上，OAuth 访问令牌本身也可以是 SVID，从而允许用户以与工作负载相同的方式向 SPIFFE 生态系统中的服务进行认证。更多内容请参阅与 OIDC 集成的相关部分。

## 密钥管理器

密钥管理器通常代表工作负载或管理员来控制、审计并安全存储敏感信息（共享密钥，通常是密码）。部分密钥管理器还可以执行数据加密和解密等附加功能。许多密钥管理器的常见特性是提供称为保险库（vault）的集中式存储，对静态数据进行加密。工作负载在执行获取密钥或解密数据等操作之前，必须逐一向保险库进行认证。

部署密钥管理器时的一个典型架构挑战是：如何安全存储工作负载用于向密钥管理器本身进行认证的凭据。这一问题有时被称为第零号凭据（credential zero）、引导凭据，或更广义地称为安全引入（secure introduction）过程。

对于依赖共享密钥的系统而言，使用密钥管理器能够提供一个安全的位置来存储、获取、轮换和吊销这些密钥，从而大幅改善系统的安全态势。然而，过度依赖密钥管理器只会延续对共享密钥的使用，而不是转向强身份机制。

### SPIFFE 与 SPIRE 如何缓解密钥管理器的挑战

如果确实需要使用密钥管理器，可以将其配置为使用 SPIFFE 证书进行认证。这样一来，你就可以使用同一套 SPIFFE 证书实现服务之间的直接认证，同时也能获取密钥以与使用非 SPIFFE 证书的系统进行通信。

## 服务网格

服务网格旨在通过为工作负载提供自动认证、授权以及强制执行 mTLS，来简化工作负载之间的通信。服务网格通常提供集成工具，以实现以下功能：

- 标识工作负载。
- 在工作负载之间代理通信，通常通过在每个工作负载旁部署代理（边车模式，sidecar pattern）来实现。
- 确保每个相邻代理都强制执行一致的认证与授权策略（一般通过授权策略引擎实现）。

所有主流服务网格产品都包含一套原生的、特定于平台的服务认证机制。

尽管服务网格可以在没有密码学身份平面的情况下运行，但这不可避免地会产生弱形式的身份，以允许服务间通信与服务发现。采用这种实现方式的服务网格既无法提供安全保障，也无法解决前文讨论的信任根身份问题。

许多服务网格产品都实现了自己的密码学身份平面，或与现有的身份解决方案集成，以同时提供传输通信安全与信任根解析。大多数服务网格产品都实现了 SPIFFE 或其部分规范。许多服务网格实现采用了 SPIFFE 规范的部分功能（包括 Istio 和 Consul，参见：https://www.consul.io/），可以被视为 SPIFFE 身份提供方。还有一些产品将 SPIRE 作为其解决方案的组件集成进来（例如 Grey Matter 或 Network Service Mesh）。

例如，Istio 使用 SPIFFE 进行节点标识，但其身份模型与 Kubernetes 特定的原语紧密耦合且完全基于这些原语。在 Istio 中，无法基于 Kubernetes 之外的属性来标识服务。IBM 对此进行了阐述：《为什么当前的 Istio 机制还不够》（参见：https://developer.ibm.com/articles/istio-identity-spiffe-spire/%23why-the-current-istio-mechanism-is-not-enough）。当需要更丰富的验证机制，或当服务需要在 Istio 之外的网格外环境中使用统一身份系统进行认证时，这就对 Istio 构成了限制，而像 SPIRE 这样的通用身份控制平面则没有此类局限。使用 SPIRE 管理工作负载身份的另一个优势在于，它还可以保护不受服务网格控制的通信。出于这些原因，许多组织会将 SPIRE 与 Istio 集成，使用 SPIFFE 身份替代 Istio 内置的身份机制。IBM 在 GitHub 上发布了一个示例项目：IBM/istio-spire: Istio identity with SPIFFE/SPIRE（参见：https://github.com/IBM/istio-spire）。

服务网格并不是 SPIFFE/SPIRE 的直接替代品——相反，它们是互补关系，由 SPIFFE/SPIRE 为网格内更高层的抽象提供身份解决方案。

明确实现了 SPIFFE Workload API 的服务网格解决方案，能够支持任何依赖该 API 的软件。能够向工作负载签发 SVID 并支持 SPIFFE Federation API 的服务网格解决方案，则可以在网格标识的工作负载与运行 SPIRE 或运行在不同网格实现上的工作负载之间自动建立信任。

## 覆盖网络

覆盖网络（overlay network）为跨多个平台的服务模拟出一个单一、统一的网络。与服务网格不同，覆盖网络使用 IP 地址和路由表等标准网络概念来连接服务。数据会被封装并在其他网络上进行路由，从而在现有网络之上构建出一个由节点和逻辑链路组成的虚拟网络。

尽管最常见的覆盖网络不具备认证功能，但最新的覆盖网络已经支持认证。然而，它们在允许服务接入之前，仍然不会对服务身份进行验证，通常只是依赖预先存在的证书。SPIFFE 非常适合为覆盖网络节点提供证书。
